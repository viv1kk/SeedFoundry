| D-31 | Event log and SSE: the log is held in memory and its seq is saved with the state, so seq carries on across a restart. `GET /api/events?after=<seq>` replays the retained events after that seq in order, then follows; `Last-Event-ID` wins over `?after=` because it is newer. Frame `id` is the seq, `event` is the type; keepalive comment every 15 s. | D-32 | Every state change runs on a copy of the state; the copy is saved to `var/state.json` (D-3), then becomes the live state, then its events are published. A refused change or a failed save changes nothing and emits nothing; a change that alters nothing (an autosave of unchanged text) emits nothing. Intake events (`intake.file_created`, `intake.file_updated`, `intake.file_deleted`) carry the file's id, name, category and size, never its content; the snapshot and `GET /api/intake/files/{id}` carry content. Replacing a core file emits a delete, then a create. File ids are `f-<n>` from a saved counter. Routes are async, so every change runs on the one event loop that also serves SSE | The disk never lags what a client has seen. A 1 MB file autosaved many times would bloat the log; only the one client writes content, so M3 can refetch it. Counter ids keep the event stream deterministic (NFR-1) | Technical (M1) |
| D-33 | A build saved as `running` when the server starts is marked `interrupted`, with a `build.interrupted` event (level WARN). Intake changes return 409 `intake_locked` while a build runs (FR-B-8), so this also releases the lock | The engine cannot resume after a restart; a stale `running` build would leave intake read-only for good | Technical (M1) |
| D-34 | FR-IN-11 at the API: 1 MB means 1,048,576 bytes of UTF-8. Import sends one file per request as the raw body (`POST /api/intake/import?filename=...&category=...&replace=...`), and the server checks those bytes: strict UTF-8 with any BOM stripped, no NUL byte, `.md` names only (FR-IN-7). Content sent as JSON (create, update) gets the same size and NUL checks, and a lone surrogate is refused. Errors: 413 `file_too_large`, 415 `not_utf8_text`, 415 `not_markdown`, each with a message the UI can show as written. Line ends are stored as `\n` | Text the browser has already decoded cannot be checked for UTF-8; a raw body needs no multipart dependency. Browsers return textarea content with `\n`, so storing `\n` stops the first autosave after an import from rewriting an untouched file | Technical (M1) |
| D-35 | Intake API: `GET /api/state`, `GET /api/events`, `GET /api/intake/categories` (categories in Ensemble order with screen labels, the FR-IN-7 filename hints and the size limit), `GET` and `POST /api/intake/files`, `GET`, `PATCH` and `DELETE /api/intake/files/{id}`, `POST /api/intake/import`. Category ids in code: `person`, `instrument_awareness`, `environment`, `music`, `misc_context`. A second file in a core category, whether by create, import or a category change, is refused with 409 `core_slot_taken` naming the existing file, unless the request sets `replace`, which deletes the existing file. Errors have the body `{"detail": {"code", "message", ...}}`. Names are trimmed, 1 to 120 characters, without `/` or `\`; they need not be unique, as files are identified by id | One copy of the category list and filename hints, served to the frontend. FR-IN-3 holds however a file reaches a core slot. Uniqueness was not asked for, so none is imposed | Technical (M1) |
| D-36 | In iteration 2 the observer feedback updates the four core files before the rebuild (A-4). Each routed segment is appended verbatim under `### Observer feedback (iteration 1)` at the end of the matched section, creating the section heading if the file lacks it. The files are really changed, not only described: the iteration 1 versions are kept with build 1 so the change can be shown. This clarifies D-5 and does not replace it: what iteration 2 fixes is still scripted, and the logs report only what the routing actually did | Stakeholder asked that the feedback visibly update the four files and the rebuild run from them. Doing the edit for real is cheap and keeps every log line true; routing by the boundary rules is the Ensemble model itself (one home per concern), and keeps the updated files boundary-clean | Stakeholder (2026-10-03); method technical |

## 3. Risks

| Id | Risk | Mitigation |
|---|---|---|
| R-1 | Defect styling leaks into SeedFoundry's own UI | `defects.css` scoped under one root class, loaded only in iteration 1 dashboard; contrast test runs on SeedFoundry UI |
| R-2 | Validators and the defect catalogue drift apart | D-14 test: sample iteration 1 finding ids equal catalogue ids; iteration 2 has zero |
| R-3 | Build feels too slow or fast on the presenter's machine | Simulated clock with weights; speed and skip controls |
| R-4 | Seed docs lack enough detail to rebuild the dashboard faithfully | M0 flags gaps; fall back to a design consistent with Seed v0.1 tokens and record it |
| R-5 | Boundary lint is noisy on real user files | Advisory only (D-12); small allowlist; rules tested against the sample |
| R-6 | Determinism broken by ordering or time | Seeded RNG, sorted iteration, `sim_t` only; determinism test from M5 |
| R-7 | Imported markdown injects HTML or script into Preview | Render with a sanitiser; test with a hostile sample |
| R-8 | Scope creep from Seed v0.1 features | Requirements §3 out of scope list; reuse notes decide what carries over |
| R-9 | Drill-down (D-29) adds a filter context, a query engine and URL sync to M7, and the defect overlay must still apply at every drill level | Overlay patches are rules over the data, not stored values, so they apply at any filter. The D-14 finding count is asserted on the unfiltered payload; a test checks the overlay is still applied at a sample of drill levels (some defects, such as N-5's doubled row, can fall outside a narrow drill). Query engine tested against row-level ground truth, as Seed v0.1's was |
